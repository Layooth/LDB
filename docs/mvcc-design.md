# MVCC 多写并发 —— 设计文档（v3，已全部落地）

> 状态：P1、P2、P3 已实施；P4 经评估取消（见 §3.8 第 5 条）。
> 多写并发（快照隔离 + 首提交者获胜 + 提交期唯一约束）已完整可用。

## 1. 现状与动机

当前架构（单写者 + 读写分离）：

```
ConnSession A ──写──▶ RwLock<Engine>（写锁）──▶ Store.txn（全局唯一事务槽）
ConnSession B ──读──▶ RwLock<Engine>（读锁）──▶ read_shared（已提交视图）
```

- 读并发已解决（RwLock + 只读句柄 + 定位读）。
- 写仍全局串行：同一时刻最多一个会话持有 `store.txn`，
  第二个写会话立即收到 `DATABASE_LOCKED`。
- 组提交已把 fsync 移出临界区，但单写者模型决定了无法重叠
  「构建脏页」这一步。

多写并发的收益场景：多个客户端同时写**不同的表**（或不同 key 区间），
理应互不阻塞。实现后写吞吐随并发近线性扩展，且长写事务不再挡住
其它会话的所有写操作。

## 2. 目标与非目标

目标：
1. 每个会话可以同时各持有一个开放事务（多写）。
2. 提交原子性、崩溃恢复语义不变（WAL 只重放已提交事务）。
3. 隔离级别：快照读（snapshot isolation）——读见事务开始前
   的已提交状态；写-写冲突在提交时检测并让后者失败。
4. 单表 ≤ 256MB 的既有上限与磁盘格式不变。

非目标：
- 串行化（serializable）隔离；跨表外键约束；分布式。

## 3. 核心设计

### 3.1 事务对象：全局槽 → 每会话槽

```rust
// Store 变更
pub struct Store {
    // 删除：txn: Option<Txn>, txn_owner: Option<u64>
    txns: HashMap<u64 /*session_id*/, Txn>,   // 每会话一个开放事务
    commit_seq: u64,                           // 单调递增，见 3.4
    ...
}
```

- `begin(owner)`：`txns.insert(owner, Txn::new())`，不再互斥。
- `commit(owner)`：冲突检测（3.3）→ 追加 WAL → 应用到全局状态。
- `rollback(owner)`：直接丢弃。

### 3.2 页可见性：版本链 → 快照指针

不引入多版本页（存储格式保持不变）。改用**快照 + 每事务页覆盖层**：

- 每个事务读取页时，按序查找：自己的 `txn.pages` →
  已提交事务的 pending 集合（按 commit_seq 排序）→ 磁盘。
- 读快照 = 事务 begin 时的 `commit_seq`。`read_shared(owner)`
  改为 `read_at(snapshot, owner)`：只应用 `commit_seq <= snapshot`
  的 pending 页，对自己再叠加 `txn.pages`。
- pending 从 `HashMap<PageKey, Vec<u8>>` 变为
  `Vec<CommittedPages { seq, pages: HashMap<PageKey, Vec<u8>> }>`，
  checkpoint 时把 seq <= 最老活跃快照 的部分合并落盘（见 3.6）。

### 3.3 写冲突检测：首写者获胜

- 每个事务记录自己的写集 `txn.dirty: HashSet<PageKey>`。
- 提交时：若「冲突集」（自己写集 ∩ 其它更晚提交事务的写集）非空，
  且对方提交序号大于本事务的快照 → 返回
  `WRITE_CONFLICT`（新错误码），调用方应重试整个事务。
- 粒度是**页级**：两事务写同一页的不同行也算冲突。
  页内行级检测需要解码比对，留作后续优化。

### 3.4 提交协议（沿用组提交管线）

```
会话（写锁外构建脏页）→ 提交时短暂拿引擎写锁：
  1. 冲突检测（3.3）
  2. 冲突通过：分配 commit_seq = ++global_seq
  3. WAL 追加字节（顺序 = seq 顺序，由写锁保证）
  4. 把事务的 pages 挂入 pending 列表（seq 有序）
  5. 释放写锁 → full 模式在锁外等 fsync 确认（现状机制）
冲突失败：丢弃脏页，返回 WRITE_CONFLICT
```

关键点：**步骤 1-4 在一个短临界区内完成**，天然全序；
WAL 记录顺序与 seq 顺序一致，恢复逻辑不变（按 commit 记录重放）。

### 3.5 内存索引与表结构

这是最难的部分。`Table.indexes`（HashMap）与 `row_count` 是共享
可变状态，当前在写语句执行时同步更新。多写下不可行：

- **延迟索引更新**：写语句只更新 `txn.pages` 和事务本地的索引
  增量（`txn.index_delta: HashMap<(index_name, key), Vec<row_id>>`），
  提交成功后在一个短临界区应用到共享索引。约束检查
  （唯一性）用「共享索引 + 自己的 delta」合并视图判断。
- `row_count` 同理延迟合并。
- 事务内读自己的写：SELECT 通过合并视图（索引 delta + 页覆盖层）
  已覆盖（3.2）。

### 3.6 checkpoint 与最老活跃快照

- checkpoint 只能落盘「seq <= 最老活跃快照」的 pending 页，
  否则会破坏进行中事务的读视图。
- 维护 `active_snapshots: BTreeSet<u64>`（begin/commit/rollback 维护），
  watermark = min(active_snapshots)，空则 = last_commit_seq。
- WAL 截断阈值照旧；WAL 不能截断到任何「pending 尚未全部落盘」
  的记录之前——与现状语义一致，只是 pending 现在是列表。

### 3.8 实测补充（P2 实施记录）

1. **语句属主必须逐语句设置**：`txn_owner` 是单字段，多写下别的会话
   begin 会覆盖它——`execute_on` 每条语句开始时调用
   `set_active_owner(owner)`（语句持有写锁期间不会被覆盖）。
   隐式事务通过 `Engine::write_as(owner)` 与语句属主保持一致，
   否则 DDL 门禁会把会话自己的隐式事务误判为「其它会话」。
2. **索引操作记录必须与真实变更一一对应**：no-op（行号本就不在
   索引列表里）不记录，否则回滚撤销会制造幽灵索引条目
   （实测踩坑：一次失败的 UPDATE 在索引里留下死行号，
   后续同 key 更新全部误报唯一冲突）。
3. **唯一约束已统一到提交期（P3 落地）**：语句期不检查唯一约束、
   不更新共享索引，只记 delta；提交临界区内顺序应用 delta 并检查
   唯一索引（撞已提交键 → CONSTRAINT_VIOLATION，语义诚实：
   键已被占用，重试无用）。并发插同键 = 首提交者获胜。
   附带收益：读路径（索引/扫描）对未提交删除的可见性不再分叉，
   读己之写通过 delta 合并实现（find_by_equality(owner)）。
4. 回滚的页计数收缩：其它开放事务动过该表时不收缩（容忍页洞，
   空闲页扫描会复用），单写者场景行为不变。

### 3.7 页分配（P4 取消说明）

原计划把页号分配挪到提交时以避免并发分配冲突。实测评估后取消：
语句期的分配本就在引擎写锁内串行，回滚通过「其它事务动过该表则
不收缩页计数」容忍页洞——空洞页读为空页，空闲页扫描会自动复用，
无正确性影响。P4 的收益（省页洞）不抵改写 WAL 记录的复杂度。

`alloc_page` 为表追加新页。两个事务并发给同一表分配页号会撞号：

- 方案 A（采用）：分配页号挪到**提交时**——事务内用负数/临时页号
  标记新页，提交临界区内统一分配真实页号并改写 WAL 记录与 pending。
  缺点：WAL 记录要在临界区里重写。
- 方案 B：begin 时预分配区间（每事务保留一段页号）。浪费空洞但简单。
- 倾向 A；临界区内的重写量 = 新页数，通常很小。

## 5. 风险清单

1. **索引竞态（3.5）**是正确性重灾区：唯一约束漏判 = 数据损坏。
   P3 必须带压力测试（N 线程插同一 key，恰一个成功）。
2. pending 列表在高频提交下变长 → 读路径线性扫描。
   上限保护：pending 条目数超过阈值时强制合并（拿写锁折叠）。
3. 写冲突重试语义对调用方是破坏性变更（原来只会 DATABASE_LOCKED），
   HTTP/LDBP 错误码与文档需同步。
4. 与 Node 版磁盘格式完全兼容（只改内存结构），但 Node 版不具备
   多写语义——不要让 Node 版打开有并发写历史的目录的**未 checkpoint**
   WAL 之外的场景，恢复语义本身一致。

## 6. 性能预期

- 写-写不同表：接近线性扩展（8 会话 → 预期 4-6 千 wps，受限于
  单条 WAL fsync 与组提交批次）。
- 写-写同页：冲突重试，退化行为取决于应用；文档必须写清。
- 读：与现状持平（快照指针开销 ≈ 一次二分/哈希查找）。
